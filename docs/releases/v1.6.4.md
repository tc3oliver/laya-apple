# laya-apple 1.6.4: `serve` reports Jev's confidence, non-sequential checkpoints are refused

A patch release. `laya-apple serve` adds a field so Jev-compatible clients can read the
confidence Jev would report, and a checkpoint trained for a non-sequential option layout now
fails loudly. `predict`, the parity tolerances, the routing rule and the prebuilt-artifact pin
are unchanged.

```bash
pip install -U 'laya-apple[ane]'
```

## `x_jev_confidence` in `serve`

Added in [#170](https://github.com/tc3oliver/laya-apple/pull/170)
([#168](https://github.com/tc3oliver/laya-apple/issues/168)). Each `choice` and `score`
answer carries `x_jev_confidence`: the `confidence` Jev would report for the same
probabilities, as upstream Laya #1066 defines it. `confidence` is unchanged and the two are
never aliased. A `noul` answer, or one without usable probabilities, gets no field. See
[`docs/serve.md`](../serve.md).

## Non-sequential `option_layout` is refused

Fixed in [#171](https://github.com/tc3oliver/laya-apple/pull/171)
([#167](https://github.com/tc3oliver/laya-apple/issues/167)). Upstream stores the layout as a
top-level `option_layout` key of `rl_agent_config.json`. laya-apple validates only sequential
semantics, so running a checkpoint trained for another layout gave wrong decisions, and an
artifact built from it looked valid. Loading such a checkpoint, and building or checking its
artifact, now raises `LayaAppleError`. A checkpoint without the key is sequential, as before.

## Limitations

- Nothing here was benchmarked. Neither change touches the model forward pass, and no
  performance claim is made.
- The [1.6.3](https://github.com/tc3oliver/laya-apple/blob/main/docs/releases/v1.6.3.md#limitations)
  limitations not repeated here still apply.

## Upgrading

No code change needed, and nothing to rebuild or re-fetch. Only a checkpoint with a
non-sequential `option_layout` behaves differently: it now raises.
