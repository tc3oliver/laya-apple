# laya-apple 1.4.0: decisions stay fast while your local LLM is busy

1.4.0 changes no runtime code. It publishes what was measured since 1.3.0, above all
`laya-apple serve` on the same Mac as a busy local LLM. With the default `--device auto`,
short single-question decisions run on the Apple Neural Engine instead of queueing on the
GPU behind the LLM. In one run on an Apple M4 Max, their P99 stayed at 47.2 ms with the LLM
generating at saturation, against 122.3 ms with every decision on the GPU.

```bash
pip install 'laya-apple[serve,ane]'
laya-apple serve                                   # http://127.0.0.1:8642
export TYPESAFE_BASE_URL=http://127.0.0.1:8642     # then run your Jev client as usual
```

The API is Jev-compatible. laya-apple is not affiliated with TypeSafe or Jev, and the
answers are Laya's, not Jev's.

## Measured results

`serve --model laya` beside `Qwen3.8-27B-oQ4e-mtp` on oMLX generating at saturation (two
streams, 256 tokens each), with 8 decision requests per second, open loop: 80% short, one
question at 96 tokens; 20% with three questions at 128 tokens. Medians over four 60 s
windows per cell (nine for the LLM alone). P99 runs from each request's scheduled arrival,
so queueing counts.

| Result | `--device gpu` | `--device auto` | Source |
|---|---:|---:|---|
| Short-decision P99, LLM busy | 122.3 ms | **47.2 ms** | [`m4-max-r2/tables.md`](https://github.com/tc3oliver/laya-apple/blob/main/benchmarks/serve/m4-max-r2/tables.md) |
| Short-decision P99, LLM idle | 55.9 ms | 43.2 ms | same |
| Three-question P99, LLM busy (idle) | 153.1 (79.4) ms | 117.1 (84.1) ms | same |
| LLM tok/s beside serve (alone: 42.2) | 40.0 (−5.3%) | 40.5 (−4.0%) | same |
| Hard mismatches / errors | 0 / 0 | 0 / 0 | same |

- **The two configurations' cost to the LLM differs by 1.31 points.** The LLM-alone windows
  of the same run spread over 1.28 points, so the difference is just above the noise.
- **Correctness:** 7,728 decisions, each compared under the FP16 gate with the same server's
  answer with the LLM idle; max probability error 0.0039.
- **About 4% of `auto` short decisions ran on the GPU** (130 of 3,144): the scheduler's
  designed spill when the Neural Engine backlog is the longer wait. The P99 includes them.
- **Run 1 was invalid.** Two of its five validity checks failed, so no result is drawn from
  it. Run 2 used two revised validity definitions, written after run 1 and before run 2's
  data, with every result criterion and limit unchanged
  ([`benchmarks/serve/README.md`](https://github.com/tc3oliver/laya-apple/blob/main/benchmarks/serve/README.md#run-1-m4-max-invalid)).

All on one Apple M4 Max, macOS 26.6.2, laya-apple 1.3.0 (the runtime 1.4.0 ships unchanged),
on 2026-09-25. The release gate for this version is in
[`benchmarks/release-gate-1.4.0.md`](https://github.com/tc3oliver/laya-apple/blob/main/benchmarks/release-gate-1.4.0.md).

## What failed

**GIL-released Core ML predict on the product mix: FAIL**
([`research/coreml-nogil-product-mix/`](https://github.com/tc3oliver/laya-apple/blob/main/research/coreml-nogil-product-mix/README.md)).
Two candidates were tested against the preregistered production gate on the v1.0
closed-loop mix: C, a thread-placed ANE whose `predict` releases the GIL, with the GPU in its
worker process; and D, the same with the GPU on a thread, with no IPC. Both failed on all
three models.

- **Passed:** correctness (0 mismatches) and GPU completion isolation everywhere. The GPU's
  return P50 fell from 4.35 ms (`laya`) and 8.53 ms (`laya-typed-decisions`) to 0.06 ms or
  less.
- **Failed:** short (ANE) P99 regressed in every cell, by 11.8% to 83.0%, and aggregate
  throughput fell below the gate in four of six cells, by up to 15.6%.
- **Production is unchanged:** thread-placed coremltools for `laya` and
  `laya-typed-decisions`, process placement for `laya-multilingual`.

## Ongoing

## Limits

- **`serve` performance is one run in one setting:** one M4 Max, one LLM server and model, a
  decode-heavy LLM load with short prompts, `--model laya`, 8 decision requests per second.
  Other LLM servers and models, prefill-heavy LLM loads, `--model auto` and other request
  rates are not measured.
- **`auto` still costs the LLM throughput,** 4.0% in that run, and only 1.31 points less than
  `--device gpu` against a 1.28-point spread.
- **Multi-question decisions always run on the GPU,** so they share it with the LLM: their
  P99 rose to 117.1 ms with `auto` while it was busy.
- **Energy use, quantized artifacts and cross-SoC validation** are still not measured.
- **Every 1.3.0 limit still applies:** no Jev accuracy claim, clients with thresholds tuned on
  Jev, `auto` routing between English and multilingual only, `instructions` required, and
  the deliberate status-code differences
  ([`docs/serve.md`](https://github.com/tc3oliver/laya-apple/blob/main/docs/serve.md#limits),
  [README](https://github.com/tc3oliver/laya-apple#limitations)).
