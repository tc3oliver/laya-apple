# laya-apple 1.7.0: an opt-in W8 ANE artifact (experimental), `serve` reports Jev's confidence

A minor release. It adds an 8-bit weight-palettized (W8) ANE artifact for `laya-typed-decisions`
L64, which you choose explicitly; FP16 stays the default and nothing changes unless you ask for
it. `laya-apple serve` adds a field so Jev-compatible clients can read the confidence Jev would
report, and a checkpoint trained for a non-sequential option layout now fails loudly. The parity
tolerances, the routing rule and the prebuilt-artifact pin are unchanged.

```bash
pip install -U 'laya-apple[ane]'
```

## Opt-in W8 ANE artifact (experimental)

Added in [#176](https://github.com/tc3oliver/laya-apple/pull/176), after the research in
[#174](https://github.com/tc3oliver/laya-apple/pull/174) and
[#175](https://github.com/tc3oliver/laya-apple/pull/175).

```bash
laya-apple artifacts build laya-typed-decisions --length 64 --quantize w8
```

```python
laya = Laya.from_pretrained("laya-typed-decisions", device="auto", ane_quantization="w8")
```

The artifact is built beside the FP16 one and runs the unchanged parity gate (probability error
<= 0.02, 0 hard mismatches), the 100% Neural Engine placement check, the runtime probe and the
hash check. L64 loads it; the other buckets keep their FP16 artifacts. It works with workers and
adaptive execution. Scope, how it fails and the full limitations are in
[`docs/guide.md`](../guide.md#opt-in-w8-ane-artifact-experimental-since-17).

Measured on macOS 27.0, Apple M4 Max, coremltools 9.0
([`research/ane-w8-l64-gate/`](../../research/ane-w8-l64-gate/README.md),
[`research/ane-w8-l64-s5-open-loop/`](../../research/ane-w8-l64-s5-open-loop/README.md)):

| | FP16 | W8 |
|---|---|---|
| Single L64 request, end-to-end P50 | 8.2 ms | 5.4 ms |
| Forward predict P50 | 1.0 | 0.651 (pooled, 3 processes) |
| Throughput, single client | 1.0 | 1.52x |
| Weights | 738.9 MB | 369.7 MB |
| Max probability error (gate 0.02) | 0.0046 | 0.0170 |
| Hard mismatches | 0 | 0 |

### Why it is experimental and off by default

The preregistered production gate for W8 was **not passed**; its recorded verdict is Research
Only / No Ship, and W8 ships here only as this explicit opt-in.
- **GPU LLM interference.** With a continuous local LLM on the GPU and a closed-loop client, the
  LLM generated about 4% fewer tokens/s next to W8 (ratio 0.953 to 0.962 in 12 of 12 cells,
  bound 0.97). An open-loop run at equal offered load found no W8-specific slowdown (1.012 to
  1.013) and a 25% higher offered load cost about 3% in both arms, so the closed-loop drop most
  likely comes from the extra GPU work the faster ANE path completes. The closed-loop cost is
  still real for a client that sends as fast as it is served.
- **No real L64 traffic data.** No recorded request corpus exists, so how often real requests
  fall in the L64 bucket is unknown. This is why W8 is not the default.
- **Adaptive breaker.** No real GPU-busy episode tripped it with W8, so its trip behaviour is
  untested.
- Two near-tie flips against the reference (listed in the research record); one machine,
  thread-level concurrency.

### Limits of the option

Only `laya-typed-decisions` L64 on Apple M4 Max with macOS 27 (other models and machines raise),
not with `device="gpu"`, `ane_startup="background"` or `from_pretrained("auto")`, and not
supported by `artifacts export`, `import`, `fetch` or `laya-apple serve`. The routing thresholds
are the FP16 ones. A missing, stale or failing W8 artifact raises; it never falls back to FP16 or
the GPU.

## `x_jev_confidence` in `serve`

Added in [#170](https://github.com/tc3oliver/laya-apple/pull/170)
([#168](https://github.com/tc3oliver/laya-apple/issues/168)). Each `choice` and `score`
answer carries `x_jev_confidence`: the `confidence` Jev would report for the same
probabilities, as upstream Laya #1066 defines it. `confidence` is unchanged and the two are
never aliased. A `noul` answer, or one without usable probabilities, gets no field. See
[`docs/serve.md`](../serve.md).

## Non-sequential `option_layout` is refused

Fixed in [#171](https://github.com/tc3oliver/laya-apple/pull/171)
([#167](https://github.com/tc3oliver/laya-apple/issues/167)). Upstream stores the layout as a
top-level `option_layout` key of `rl_agent_config.json`. laya-apple validates only sequential
semantics, so running a checkpoint trained for another layout gave wrong decisions, and an
artifact built from it looked valid. Loading such a checkpoint, and building or checking its
artifact, now raises `LayaAppleError`. A checkpoint without the key is sequential, as before.

## Limitations

- The `serve` and `option_layout` changes were not benchmarked; neither touches the model forward
  pass. The seven Jev clients tested for `serve` were not re-run against the extra
  `x_jev_confidence` field ([`docs/serve.md`](../serve.md)).
- The W8 numbers are one machine (Apple M4 Max, macOS 27.0). The release benchmarks of FP16 are
  not re-run for this release.
- The [1.6.3](https://github.com/tc3oliver/laya-apple/blob/main/docs/releases/v1.6.3.md#limitations)
  limitations not repeated here still apply.

## Upgrading

No code change needed and FP16 behaves as before. A checkpoint with a non-sequential
`option_layout` now raises. To try W8, build the artifact locally as above; it is not part of the
prebuilt-artifact pin.
