# ANE cost at a fixed GPU load

Issue: [#45](https://github.com/tc3oliver/laya-apple/issues/45), round 2. Round 1:
[`../coreml-gil-completion-path/`](../coreml-gil-completion-path/README.md) (#46).
Machine: Mac Studio M4 Max, Python 3.12.14, coremltools 9.0, PyObjC 12.2.2. Model:
laya-typed-decisions. Every number below is in `results.json` / `tables.md`, generated by
`scripts/analyze.py` from `raw/`.

## Question

Round 1 showed that releasing the GIL around Core ML `predict` (C) removes the GPU completion
delay. It also measured the ANE losing 13.5% of its throughput against the product path (A),
and the process placement (B) losing 9.0%. Both measurements had one confound: the GPU
client was closed loop. Once the GPU was unblocked it sent 44% more requests, so the ANE
shared the machine with more GPU work.

**At the same GPU offered load, what does each configuration cost the ANE?**

## Answer

**At a fixed GPU load, none of the three configurations costs the ANE a measurable amount.**
Against A, with the GPU busy:

| | ANE req/s | vs A | ANE e2e P99 | vs A |
|---|---|---|---|---|
| A thread + coremltools | 97.5 | – | 10.79 | – |
| B process + coremltools | 98.0 | **+0.5%** | 10.59 | ×0.98 |
| C thread + PyObjC, GIL released | 97.6 | **+0.1%** | 10.63 | ×0.99 |

- Round 1's −13.5% (C) and −9.0% (B) came from the GPU running more requests, not from the
  binding or the placement. With the GPU held at the same requests and arrival times, both
  are within ±0.5% of A. C against B: −0.4% throughput, P99 ×1.00.
- C now meets #45's ANE criteria:
  - throughput regression < 5%: +0.1%;
  - no clear tail regression: e2e P99 ×0.99, `predict` P99 10.22 vs 10.20 ms.
- The GPU completion path is the same in B and C:
  - return leg P50 0.035 / 0.037 ms, P99 0.125 / 0.203 ms (A: 7.68 / 8.96);
  - GPU e2e P99 74.9 / 75.1 ms (A: 440.9).
- Process placement is **not** clearly better than C (#45 Case C does not apply). Their ANE
  and GPU numbers differ by less than the cycle-to-cycle spread.

This holds at this GPU load (46.65 req/s offered). Round 1 compared B and C at 70–73 req/s,
where C's ANE was 4.9% below B's. That comparison was not at equal GPU load, and this round
did not re-test the higher load (see Limits).

## Workload

- **GPU:** L128, 1 question, open loop, Poisson at a target of 45 req/s.
  - The stream's RNG is seeded the same way (seed 17) in every window, so every window of
    every configuration schedules the same 1,020 arrivals at the same offsets with the same
    request seeds.
  - 933 of them fall inside the 20 s measurement span: 46.65 req/s realized in-window,
    above the 45 target, which is what seed 17 draws.
- **ANE:** L128, 1 question, closed loop (one client).
- **Cells:** ANE alone (closed), GPU alone (open), both at once.
  - 3 cycles × 20 s, with the harness's 2 s warm-up per window.
  - The Core ML E5 cache is shared and was not cleared.
- **Configurations:**
  - A: ANE on a thread, coremltools (the product path);
  - B: ANE in a worker process, coremltools;
  - C: ANE on a thread, PyObjC `predict` with the GIL released (`nogil_predict.py` from
    round 1).
  - Run one after another, oMLX stopped.

`scripts/run_fixed.py` reuses round 1's `run_cell.py` (the gpu-ane-interference harness, the
`--ane-predict` switch and the GPU reply stamps). It replaces only the device plan's cells and
records each window's scheduled GPU arrivals.

### Workload equality (checked before any ANE comparison)

| | A | B | C |
|---|---|---|---|
| scheduled GPU arrivals per window | 1,020 | 1,020 | 1,020 |
| arrival SHA-256 (offsets ns + request seeds), every window | `b98fee08a0a07d5b…` | same | same |
| GPU offered in-window | 46.65 req/s | 46.65 | 46.65 |
| GPU completed within the window | 46.35 req/s | 46.60 | 46.60 |
| GPU errors / answer mismatches | 0 / 0 | 0 / 0 | 0 / 0 |
| trace ↔ backend join | 19,295/19,295 | 19,258/19,258 | 19,220/19,220 |

The same arrival trace (identical SHA-256) was used in all three configurations and in every
cycle.

**A submits later than scheduled.** In A, a submission scheduled while `predict` holds the
GIL leaves late (generator lag P99 9.64 ms; B/C 0.27/0.30). The scheduled trace is identical,
but the GIL delays A's actual submit. That delay is part of A's cost, and it is not a
difference in offered load.

### Queue stability (rule fixed before the runs)

In every cycle of the concurrent cell, the GPU stream must:
- have 0 errors;
- complete ≥98% of its offered in-window rate within the window;
- have a last-quarter mean queue delay ≤ max(2 × the first quarter's, the first quarter's
  + 20 ms).

All 9 cycles pass. A is close to saturation, though: its GPU occupancy is ~20.4 ms at a
realized 46.65 req/s (utilization ≈ 0.95).
- A's queue mean by quarter swings 64 / 218 / 233 / 72 ms, and the queue P99 is 420 ms.
- B and C: 8 / 15 / 7 / 7 ms, queue P99 62 ms.

A 20 s A-only pilot at the same settings, run before the campaign and not in `raw/`, looked
the same, and the rule passed there too. So the rate was kept at 45 and not lowered to 42.
This does not affect the ANE comparison: in all three configurations the GPU receives the same
forwards, and `mx.eval` is 12.25 / 12.14 / 12.15 ms.

In A the GPU looks "busy" 95% of the time because its occupancy includes the ~7.7 ms wait for
the GIL; B and C hold the GPU 59% of the time for the same work.

The GPU reply boundary reproduces round 1:
- A: 2,798 of 2,799 GPU forwards ended inside an ANE `predict`. The reply was read a median
  7.604 ms after the forward ended, and the wait correlates with the `predict` time left
  (0.96).
- B / C: 0.022 ms, correlation 0.02 / −0.13.

### How much of round 1's −13.5% was the GPU load

- **Round 1:** C −13.5% and B −9.0% against A. A's GPU ran 48.1 req/s, C's 69.5 and B's
  72.5, all closed loop.
- **This round:** every GPU at the same 46.65 req/s offered. C +0.1% and B +0.5% against A.
- **Within the ±1% resolution of these runs, all of round 1's ANE regression came from the
  GPU running more work.**
- Each configuration's ANE also slows by ≤1.6% next to the GPU at this load. In round 1 the
  slowdown against the ANE alone was 3.1% (A, GPU at 48.1), 10% (B, 72.5) and 15.7% (C,
  69.5). The ANE's slowdown grows with the GPU's request rate, whatever the binding.

Also seen, and not investigated: the GPU alone at this open-loop rate is slower than with the
ANE busy (service mean ~14.1 vs 12.6 ms, `mx.eval` P99 19.1 vs 12.5). That is consistent
with the idle-machine power-state effect recorded in the gpu-ane-interference study.

## Interpretation against #45's cases

- **Case A applies.** At a fixed GPU load, no-GIL (C) costs the ANE +0.1% and no tail. Round
  1's −13.5% was mostly the GPU-load confound. No-GIL remains a production candidate.
- **Case B does not apply.** C is not >5% worse.
- **Case C does not apply.** Process placement is not clearly better than C: GPU completion,
  ANE throughput and ANE tail are equal within noise.

This round does not choose between B and C. What separates them is outside these runs:
- PyObjC as a runtime dependency;
- CPU per ANE request: B 0.57, C 0.65 ms;
- start-up, memory;
- behaviour at a higher GPU load.

## Limits

- **One GPU load, near A's saturation.** B and C were not compared at equal load at 60–70
  req/s, where round 1 (not load-matched) put C 4.9% below B. GIL contention in C could grow
  with GPU request rate (more Python work on the dispatcher and client threads per second).
  This round cannot rule that out.
- **One run per configuration, 3 cycles.** Cycle-to-cycle spread of ANE requests per window
  was ≤7 (≤0.4%), so the ±0.5% differences above are at the resolution limit.
- **No product routing.** Every stream targets its device explicitly, so routing is not
  exercised.
- **Not measured:** memory, start-up and IPC under load beyond `dispatch + return`, per
  #45's instruction to measure them only if process placement wins.
