# ANE process placement: acceptance gate

Issue: [#52](https://github.com/tc3oliver/laya-apple/issues/52). Machine: Mac Studio M4 Max,
64 GB, Python 3.12.14, coremltools 9.0. Every number is in `results.json` / `tables.md`,
generated by `scripts/ane_placement_gate_report.py` from `raw/`
(`scripts/bench_ane_placement_gate.py`, `run.sh`). Nothing in the runtime or its defaults
changes here.

## Question

The research in #45 (#46, #51) showed:
- a thread-placed Core ML `predict` holds the GIL and delays the GPU's completion path;
- at equal GPU load, process placement removes this with no measurable ANE cost.

Are process placement's resource and lifecycle costs acceptable?

## Result: **FAIL** under the criteria written before the data

| model | correctness | isolation | memory | start-up | CPU | IPC | shutdown | lifecycle | orphan |
|---|---|---|---|---|---|---|---|---|---|
| laya | pass | pass | pass | pass | **FAIL** | pass | pass | pass | pass |
| laya-typed-decisions | pass | pass | pass | pass | **FAIL** | pass | pass | pass | pass |
| laya-multilingual | pass | pass | pass | pass | pass | pass | pass | **FAIL** | pass |

The two failures, and what the evidence says about them:

1. **CPU:**
   - **Result:** tree CPU per request with both devices busy is ×2.7 (laya) and ×2.9
     (laya-typed-decisions) the thread placement's; the limit was ×1.5. laya-multilingual:
     ×0.88.
   - **Location:** the GPU worker, at 6.46 / 6.44 against 2.72 / 2.57 ms of CPU per GPU
     request. With the GPU alone, both placements cost the same (≈2.5 ms).
   - **The smoke is closed loop:** unblocking the GPU lets it run 16–19% more requests
     alongside the ANE. This is the confound #51 removed for the ANE. The existing data
     shows CPU per forward follows the GPU's operating point, not the placement:
     - **#51, equal GPU offered load:** GPU forward CPU with the ANE busy is 1.67 (thread),
       1.61 (process) and 1.61 ms (thread + no-GIL); ANE CPU is 0.65 / 0.57 / 0.65 ms.
     - **#46, closed loop, GPU unblocked:** GPU forward CPU is 1.81 (thread), 3.69 (process)
       and **4.54** ms (no-GIL); ANE 0.74 / 1.38 / **1.96**. The no-GIL path pays at least
       as much.
     - This run's laya-multilingual thread row shows the same variability: the GPU worker
       spends 5.73 ms per request there, against 2.00 in a first run discarded for a
       measurement bug (below).
   - **What the gate did not do:** it did not measure CPU at equal GPU load for these
     models. The CPU criterion as run cannot tell a placement cost from a load difference.
     Nothing in it favours the no-GIL alternative.
2. **Lifecycle, laya-multilingual:**
   - **Result:** parent RSS over 10 create/serve/close iterations is 706 → 753 MB (+6.7%;
     the limit was +5% from the 2nd iteration to the last).
   - **Shape:** 699, 706, 758, 758, 758, 758, 738, 765, 765, 753. One step at the 3rd
     iteration, then flat; not steady growth.
   - **Comparison:** the thread placement grows steadily for the same model (1,113 → 1,308
     MB, then a drop to 1,244).
   - **Status:** laya-multilingual already ships with process placement, so this is not a
     new cost of switching.

## What passed

- **Isolation:** the thread placement blocks the GPU completion path for all three models.
  Process placement removes it (smoke: GPU L128 closed loop with ANE L64, each model's
  smallest bucket, closed loop).

  | model | GPU return P50, alone | thread, with ANE busy P50 / P99 | process, with ANE busy P50 / P99 |
  |---|---|---|---|
  | laya | 0.027 | 3.866 / 7.063 | 0.133 / 0.559 |
  | laya-typed-decisions | 0.027–0.029 | 3.774 / 5.216 | 0.128 / 0.515 |
  | laya-multilingual | 0.024–0.025 | 3.147 / 5.474 | 0.071 / 0.554 |

  - The wait is shorter than #46's 7.7 ms because L64 `predict` calls are shorter than L128.
  - GPU e2e P99, thread → process: laya 22.89 → 15.63, typed 18.56 → 15.60, multilingual
    15.30 → 8.83 ms.
- **Correctness:** 0 answer mismatches in every window, both placements, all models. Answers
  are compared with inline references computed in a separate interpreter.
- **Memory** (`phys_footprint` at window ends; tree = parent + GPU worker (+ ANE worker)):

  | model | thread tree | process tree | Δ | ANE worker | parent, thread → process |
  |---|---|---|---|---|---|
  | laya | 1,620 | 1,856 | +236 MB | 356 | 396 → 274 |
  | laya-typed-decisions | 1,630 | 1,858 | +228 MB | 357 | 404 → 274 |
  | laya-multilingual | 1,802 | 1,984 | +182 MB | 625 | 861 → 417 |

  - Peak tree footprint: process 1,884 / 1,884 / 2,109 MB.
  - Criterion: Δ ≤ 500 MB.
- **Start-up:**
  - Create/close loop, P50 of 10, `device="auto"`: thread 1.83–1.90 s, process 2.68–2.78 s,
    +0.85–0.88 s.
  - Smoke ANE instance: laya 3.72 → 2.67, typed 1.87 → 2.73, multilingual 2.67 → 2.64 s.
    These are single samples, and the first includes cold file caches.
  - Criterion: ≤ +2.0 s.
- **IPC:**
  - ANE dispatch + return is 0.15–0.21 ms per request (thread: 0.003–0.011).
  - The GPU gains on the order of a millisecond at the median and more at the tail, so this
    cost is small by comparison.
- **Shutdown:**
  - `close()` takes 0.23 s with process placement against 0.03–0.04 s with a thread. It
    joins the worker processes.
  - No worker is alive or zombie after any close.
- **Lifecycle, process placement:**
  - Open file descriptors stay at 3 → 3 and threads at 1 → 1.
  - No child process or zombie survives any of the 10 iterations.
  - Parent RSS: laya +0.7%, typed +0.3%.
- **Orphans:** process-placed workers exit after an exception inside `with Laya(...)`, and
  after the parent is SIGKILLed (EOF on the connection) within 0.21–0.22 s, for all models.
- **Existing runtime tests** pass (44):
  - `tests/integration/test_workers.py` (close idempotence, a killed GPU worker, close during
    background start-up, both placements);
  - `test_no_silent_fallback.py`;
  - `test_request_trace_workers.py`.

## Observations outside the gate

These are reported, not judged:
- **ANE throughput in the closed-loop smoke:**
  - laya and typed: ANE −11% / −12.5% with process placement. The GPU runs 16–19% more
    requests there, the #46 confound.
  - laya-multilingual: process is ahead on both devices (GPU 80.0 → 127.0 req/s, ANE
    160.1 → 187.3).
- **Thread placement's parent RSS jumps between create/close iterations:**
  - laya: 390 → 507 MB at the 3rd iteration, then flat.
  - laya-multilingual: steady growth.
  - The runtime's lifecycle with a thread-placed ANE may hold memory across instances. Not
    investigated.

## The current placement policy (for the decision, not changed here)

- `scripts/derive_placement.py` chooses each model's ANE placement from the v0.2 Part A
  closed-loop mix (`benchmarks/v0.2/placement-<model>-{thread,process}.json`).
  - It takes the placement with the lower heterogeneous **short-stream P99**.
  - If the two P99s are within 5%, the higher aggregate req/s wins, then `thread`.
  - The GPU is always `process`.
- Result in `laya_apple/data/placement.json`: laya → thread, laya-typed-decisions →
  thread, laya-multilingual → process.
- It does not score:
  - the GPU's completion delay, the cross-device effect measured here and in #46/#51;
  - memory, start-up, CPU or IPC.
- Changing the default would touch:
  - `derive_placement.py`, `placement.json` and its `--check`: CI, the routing-freshness
    test and the release gate;
  - `scripts/compare_bench.py`'s choice of placement files;
  - the docs that state the mapping.

## Changes of method (disclosed)

- **Discarded first run.** macOS denies USS for other processes, children included, so no
  worker memory was recorded. The inline reference models were also loaded in the
  measuring process and inflated its memory.
  - Fix: the memory criterion uses the same 500 MB threshold on `phys_footprint` (read with
    `/usr/bin/footprint`); references are computed in a child interpreter.
  - The smoke runs were re-run. The lifecycle and orphan runs were kept: they use neither.
- **Criteria changed after the first run, before the re-run's data.** Lifecycle and shutdown
  are now judged on the process placement only: the gate is about process placement, and
  thread is the incumbent it is compared with. Under the original wording, thread's own
  +29.9% (laya) and +10.6% (laya-multilingual) growth would also have failed the gate.
- **The CPU criterion is unchanged,** and it fails as reported.

## Reproduce

```sh
# ~25 min, idle machine on AC power, other GPU/ANE services stopped
LAYA_APPLE_CACHE=... HF_HUB_OFFLINE=1 sh benchmarks/ane-placement-gate/run.sh
```
