# ANE process placement: CPU at an equal GPU offered load

Issue: [#52](https://github.com/tc3oliver/laya-apple/issues/52). Follows the acceptance gate in
[`../ane-placement-gate/`](../ane-placement-gate/README.md) (#54). Machine: Mac Studio M4 Max,
64 GB, Python 3.12.14, coremltools 9.0. Every number is in `results.json` / `tables.md`,
generated by `analyze.py` from `raw/` (`run_tree_cpu.py`, `run.sh`). Nothing in the runtime,
its defaults or `placement.json` changes here.

## Question

The #54 gate failed its pre-registered CPU criterion for laya and laya-typed-decisions: whole-tree
CPU per request with process placement was ×2.7 / ×2.9 the thread placement's (limit ×1.5). That
smoke was closed loop, and process placement let the GPU complete 16–19% more requests, so it
could not separate a placement cost from a load difference.

**At an identical GPU offered load, does process placement intrinsically cost > 1.5× CPU?**

## Answer: no

| model | thread tree CPU ms / request | process | ratio | criterion ≤ ×1.5 |
|---|---|---|---|---|
| laya | 1.82 | 1.80 | **×0.99** | pass |
| laya-typed-decisions | 1.80 | 1.83 | **×1.02** | pass |

- The workload was identical, with no new correctness or stability problem (below).
- The CPU failure in #54 was caused by the closed-loop workload, not by process placement's
  intrinsic cost.
- **#54's verdict stays FAIL.** This run adjudicates one criterion of that gate under the
  condition it was meant to measure. It does not rewrite the gate's result.

## Workload

- #51's harness, unchanged (`research/coreml-placement-deconfounding/scripts/run_fixed.py`).
  - GPU: L128 open loop, Poisson at a 30 req/s target. The same seeded arrival trace runs in
    every window.
  - ANE: L128 closed loop, one client.
  - Cells: ANE alone, GPU alone, both at once, 3 cycles × 20 s each, with a 2 s warm-up.
  - Configurations: A = ANE on a thread; B = ANE in a worker process. Both use coremltools
    (the product path); no PyObjC and no no-GIL path is measured.
  - Runs went one after another with oMLX stopped; the Core ML E5 cache was not cleared.
- **Rate:** 30 was chosen before the campaign, below #51's 45. At 45, A was close to
  saturation (utilization ≈ 0.95). A single 8 s pilot at 35 req/s passed the stability rule, but
  A's queue was still rising. The pilots are not in `raw/`.
- **The one addition** is `run_tree_cpu.py`. While each window runs, a thread in the parent
  reads user + system CPU time of the parent and of every child process every 50 ms. The
  analysis interpolates those readings at the window's measurement bounds.
  - Both placements pay this sampler's own CPU (in the parent).
  - A worker whose CPU cannot be bounded over the span is an error, not a gap.

## Where the CPU goes (both devices busy, sum of 3 windows)

| | parent | GPU worker | ANE worker | tree | GPU done | ANE done |
|---|---|---|---|---|---|---|
| laya, thread | 8.75 s | 4.72 | – | 13.47 | 1,893 | 5,529 |
| laya, process | 5.98 | 4.32 | 3.52 | 13.82 | 1,893 | 5,775 |
| typed, thread | 8.59 | 4.75 | – | 13.34 | 1,893 | 5,537 |
| typed, process | 6.08 | 4.34 | 3.52 | 13.94 | 1,893 | 5,734 |

- **GPU worker, per GPU request:** 2.49 → 2.28 ms (laya), 2.51 → 2.29 (typed). The GPU worker
  in #54 spent 6.46 / 6.44 ms per request under a closed loop. At equal load it costs no more
  with process placement.
- **ANE side (parent + ANE worker), per ANE request:** 1.58 → 1.65 ms and 1.55 → 1.67 ms,
  +4% / +8%. This is the IPC and the second interpreter.
- **Tree CPU per second** is +2.6% (laya) and +4.5% (typed). The process runs also complete 4.4% /
  3.6% more ANE requests.
- **Per-forward CPU on the GPU's executing thread** is 1.64 → 1.59 and 1.63 → 1.60 ms. This
  matches #51 (1.67 → 1.61).

## Sanity checks

- **GPU return leg, P50 / P99:**
  - thread: 7.46 / 11.50 ms (laya), 7.50 / 11.38 (typed);
  - process: 0.033 / 3.19 and 0.034 / 3.07.
  - This reproduces #54's and #51's completion-path result at this load.
- **ANE req/s with the GPU busy:** 92.2 → 96.2 (laya), 92.3 → 95.6 (typed).
- **Answer mismatches:** 0 in every cell.

## Observations outside the question

These are reported, not investigated:
- **ANE alone.** laya's ANE alone runs 92.7 req/s with a thread and 98.1 in a process
  (typed: 93.2 / 97.1). #51 saw 99.1 / 98.3 for typed at the same shape, so the thread-side gap
  here may be run-to-run variation.
- **GPU alone.** At this open-loop rate the GPU alone costs far more CPU per request than with the
  ANE busy: GPU worker 7.6–7.8 ms against 2.3–2.5. The placements are equal there. This is
  consistent with the idle-machine power-state effect recorded in #51 and the
  gpu-ane-interference study. The same effect is why CPU per request is not comparable across
  different operating points, which is what #54's closed-loop criterion did.

## Limits

- **One GPU load** (31.55 req/s realized), **two models**. laya-multilingual was not run; it
  already ships with process placement and passed #54's CPU criterion (×0.88).
- **3 cycles × 20 s per configuration**, one run each.
- **The mechanism is not identified.** This run does not explain why the closed-loop GPU worker
  in #54 cost ×2.4 per request. It shows only that, at equal offered load, the placement does
  not.

## Reproduce

```sh
# ~16 min, idle machine on AC power, other GPU/ANE services stopped
```
